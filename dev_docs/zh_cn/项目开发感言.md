## 起源

该项目起源于我的一个想法。作为程序员，经常与终端打交道，我便思考：能不能在终端里面玩游戏？答案自然是可以，而且市面上也有不少库实现了这一功能。但我感觉这些库，有些过于陈旧、适配性差，有些集成度太低，又或者极度依赖特定语言的编译环境，不便直接使用。于是我想，不如自己写一个可以跨平台、稳定运行的终端游戏库。

于是，这个想法就这么敲定了。

## 选择技术栈

首先是技术栈的选择。我起初考虑了 C、C++、Go、Python、TypeScript 这五门语言，但花了五天与 AI 交流后，发现了几个问题：C 写起来难度高，C++ 较为繁琐，Go 的终端库支持不够全面，Python 的打包方案尚不成熟，TypeScript 依赖的 Node.js 显得笨重。于是，我挑中了 Rust，这也是我第一次接触 Rust，之前从未使用过，只听说过现在很多终端程序都是用 Rust 写的。

至于为什么选 Lua 作为胶水语言，是因为我从一开始就想制作一个可扩展的终端游戏引擎。同样在和 AI 聊过之后，选定了 Lua，而 Rust 本身也有 mlua 库提供支持。

但不得不说，Rust 虽然写起来有些麻烦，但在跨平台构建、Cargo 工具链、生命周期安全等方面，确实独一档的出色。

## AI（Vibe Coding）

关于 AI，这个话题比较敏感，所以我还是提前说清楚为好。
我承认，这个项目大约 90% 的代码是由 AI 生成的。这究竟算好事还是坏事，我至今也没有定论。AI 写得又快又准，但至于整体代码质量，就见仁见智了。
不过，所有的提示词、架构设计，以及初期的架构决策，都是我自己完成的。因此，在整个项目中，我扮演的角色更像是“除了亲手写代码之外的其他角色”。

在项目正式发布前，我对全部代码进行了一次通读，补充了注释，并清理了那些看起来非常冗余的部分（比如未使用的死代码等），避免给日后阅读代码的人带来不必要的困扰。

我也清楚，AI 的强大是建立在我自身的基础之上的。只有我自己明确需求、写好提示词，并亲自 Debug 和 Review 代码、找出问题，代码的运行与构建才能真正掌握在自己手里。

## 两次重构

接下来我会简要回顾前两个版本的重构经历，以及为什么要重构。

**首个版本**

第一个版本，也就是 release 中的 1.0 版，是整个项目最早的雏形实现，只具备基本的 UI 和几个经典游戏的实现。  
这个版本在架构上并没有什么突破，也没有做针对性的优化，纯粹是为了“把功能跑起来”。借助 AI，只用了两周就完成了，之后花了一周左右修 Bug，随后又断断续续添加了一些游戏，前后总共大约用了一个月时间。  
在这个过程中，我也顺便熟悉了 GitHub 的工作流，不再需要单独配置各种环节，一次性完成了编译、打包和 Release 发布。

**第一次重构**

这次重构源于第一个版本在继续扩展时暴露出的几个问题：

1. **模组系统难以编写**  
   1.0 版本的游戏全部是硬编码的，尽管 script 目录下使用了 Lua 文件作为脚本，但本质上还是要在宿主程序中写死注册表，完全没有包管理机制。如果强行扩展，一是会让 Lua VM 变得很不安全，二是后续扩展 API 也会非常麻烦。

2. **按键系统难以扩展**  
   最初使用的是 crossterm，但对游戏来说，需要更灵活的按键类型。crossterm 的缺点是无法单独识别 Ctrl、Shift 这类修饰键，而且对字符按键过于敏感，比如字母会区分大小写。

3. **架构完全没有规划**  
   如之前所述，第一个版本完全以“能跑起来”为目标，根本没对渲染、系统等方面做对应优化。导致后续扩展任何一个新内容都会牵一发而动全身，是典型的“高耦合低内聚”，代码质量相当糟糕。

因此，在进入本次重构之前，我必须先对程序架构做一次详细的初步规划，否则只会再次重蹈覆辙。  
首要问题就是：**程序的运行生命周期是怎样的？**  
第一个版本几乎没有明显的阶段划分，而这是解耦的第一步，虽然简单但非常重要：

1. **Booting**（启动阶段）—— 加载程序到内存，分配硬件资源。  
2. **Initialization**（初始化阶段）—— 加载实际使用的硬盘数据，对全局资源进行处理和配置，启动所有服务。  
3. **Runtime**（运行阶段）—— 程序实际运行阶段，所有主要业务功能都在此处理。  
4. **Shutdown**（关闭阶段）—— 释放资源，停止程序运行。

在我当前（第二次重构后）的架构中，将 Booting 和 Initialization 合并为 Boot 阶段，但内部仍然区分这两个子阶段，合并只是为了简化文件树。  
这种划分直接保证了我能够掌控生命周期，并将对应的服务放置在合适的阶段。  
第一次重构的进步，主要体现在初始架构的搭建上。

**第二次重构**

这次重构产出的就是当前版本。第一次重构的缺点也非常明显，我的确发现了大量服务层面的问题，虽然架构搭建和后续扩展开始有了“高内聚”的倾向，但仍然陷在“高耦合”的陷阱里。  
通过 git 历史可以看到第一次重构时的 `old_src/` 目录，当时 runtime 下的各个服务之间依旧相互冲突、彼此牵制，甚至有些功能连我自己都不理解，AI 生成的内容乱七八糟，实在让人看不下去。

本次重构的第一件事就是：初始地基，由我自己来写。  
说实话，挺难想象的，在历经三个月的 Vibe Coding 之后，我居然还会“古法编程”。手感倒也没有完全生疏，只是真的上手写 Rust 时，变量、生命周期与所有权这些问题直接让我飞起来了。

接着，每个服务我都尽可能去找开源库参考，自己先把整个运行过程理解透彻，再单独提取出来实现，经过测试后并入主工程。

每一次重构，都是对我整体架构理解的一次考验，也是我对每个底层服务细节的重新认识与设计。  
纯粹让 AI 全部代写，根本不可能实现。我必须主导整个项目的全局观，如何实现也必须由我通过提示词来精确描述和加以限制。

接下来，我将针对本次重构到发布为止的架构与服务进行详细讲解，也会讲述每个服务我是如何学习并设计出来的。

## 什么是 TUI？

既然是终端程序，就必须区分 TUI 与 GUI 的区别，这也是后期画布（Canvas）服务的核心要点。  
画布服务是我思考得最久的一个部分，这里我直接给出自己探索出来的答案：

1. TUI 的基本组成是“字符”（Char），GUI 的基本组成是“像素”（Pixel）。  
2. “字符”既是单位也是材质，更是唯一的笔触；所有的线条、形状，均由“字符”的样式组合而成。  
3. TUI 类似于像素画的格子拼接，但“字符”拥有自己不同于像素画的特性：  
   - 字符有自己的宽度（0、1、2，甚至有些大于2）；  
   - 字符的宽高比并不固定（大约为 1:2 宽比高）；  
   - 字符形态各异（本项目支持 Unicode 字符表）；  
   - 字符之间不存在透明叠加，只有完全覆盖。

因此，对 TUI 来说，所有布局都有强制性的对齐要求，材质也无法随意更改，通常只能通过颜色和字体样式来表现。相对于 GUI，TUI 的布局精细度肯定比不过 GUI，本质上就是由字符拼接出来的画面。  
但正是因为早期计算机系统的发展，ASCII 艺术逐渐成为一种主流风格；如今配合 Unicode 对字符表的极大扩展，我相信各位创作者完全可以用“字符 + 字体样式 + 文本颜色”构建出别具一格的画面。

## 架构

尽管刚才已经讲过了基本架构，这里还是结合当前的目录结构，对各部分做一个总结。

**生命周期**：
- **Boot**：资源初始化阶段，所有读取持久化文件、启动核心、初始化服务的工作均在此处完成。
- **Runtime**：运行阶段，主循环在此执行，所有业务处理均发生在这里。
- **Shutdown**：结束阶段，释放资源，最后一次确认所有配置已正常写入，并判断退出属于异常退出还是正常退出。

**核心与服务**：
- **core**：核心目录，包含所有最底层的世界运行环境。
- **service**：服务目录，所有额外的服务功能都在这里创建、调用与处理请求。

## 核心

### 世界时钟（WorldClock）

这个核心的功能很简单，就是获取当前时间、计算时间差值（增量），简单的实现，但决定了后面计时器（Timer）和帧（Frame）的两个关键服务与核心的运行。

### 帧运行（Frame）

这个核心的功能同样很简单，但是他的重要在于，这是限制程序频率运行的核心，保证程序的心跳稳定，每一个循环按照相同的间隔进行运行，检测每一帧的运行时间是否正常，并记录帧数。
